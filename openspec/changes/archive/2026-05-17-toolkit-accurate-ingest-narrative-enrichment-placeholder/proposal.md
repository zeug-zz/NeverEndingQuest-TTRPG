# Proposal: Toolkit Accurate-Ingest Narrative Enrichment Placeholder

## Problem

Accurate ingest now preserves source structure through source graph extraction, multi-pass normalization, repair, review approval, blueprint handoff, and build-fidelity gates. The next risk is mixing post-build narrative enrichment into that source-faithful pipeline without a hard boundary.

Past manual module enrichment work, such as Ancients Lab multi-playline expansion and Deepvault interpretive stance framing, is useful for richer modules. However, if enrichment is introduced without explicit source-lock rules, it can rename required NPCs, replace source plot topology, alter puzzle rules, or lower source fidelity after the pipeline has already passed.

## Objective

Create an artifact-only narrative enrichment placeholder contract for accurate-ingest builds. The first implementation SHALL allow the toolkit to record whether enrichment is planned, which profile is selected, which fields would be eligible, and what source-lock constraints apply, without applying any enrichment patches.

## Non-Goals

- MUST NOT auto-apply enrichment to module JSON.
- MUST NOT call LLM providers to generate enrichment text in this slice.
- MUST NOT mutate generated modules, schemas, prompts, `ModuleBuilder`, or `ModuleGenerator` in this planning change.
- MUST NOT weaken source-fidelity gates, review approval gates, or publication readiness gates.
- MUST NOT treat enrichment as required for accurate ingest completion.
- MUST NOT duplicate, bypass, or relocate existing Homebrewery `MODULE_SUMMARY.md` generation; that remains owned by the toolkit finisher path.

## Proposed Change

Define a future `narrative_enrichment_plan.json` artifact with default profile `none`. The plan records profile selection, eligibility, source-lock constraints, and non-applicability reasons. It may be generated only after build/source fidelity has no blockers.

The change also defines builder-ready implementation tasks for a later apply step: helper artifact model, report integration, optional UI/status surfacing, and tests.

Existing human-readable adventure markdown generation remains unchanged: `MODULE_SUMMARY.md` is already generated by the toolkit finisher after successful build/readiness/fidelity progression and served by the existing download endpoint. This enrichment placeholder may reference that artifact in future metadata, but it SHALL NOT regenerate or replace it.

## Risks

| Risk | Mitigation |
|---|---|
| Enrichment replaces source truth. | Source-lock requirements block plans that would alter required source NPCs, locations, plot topology, puzzle rules, or evidence. |
| Users assume enrichment is automatically applied. | The first implementation is explicit no-auto-apply and artifact-only. |
| Accurate ingest becomes dependent on enrichment. | Default profile is `none`; accurate ingest remains complete without enrichment. |
| Scope expands into runtime generation. | Runtime mutation, provider calls, and field patching are non-goals for this slice. |

## Rollout

1. Scaffold the artifact contract and specs.
2. Implement artifact-only plan generation behind a feature flag in a later apply step.
3. Surface the plan as reviewable metadata, not as source mutation.
4. Defer any auto-apply or provider-backed enrichment to a separate OpenSpec change.
